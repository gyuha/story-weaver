# 2026-08-01 — 스트리밍 취소 회계 (취소된 생성을 로그·예산에 남기고, 기획의도 취소가 실제로 멈추게 함)

## Plan vs actual

- **계획대로 된 것**: 골격이 그대로 성립했다. 슬라이스 4개 전부 red를 먼저 보고 구현했고(1건 예외 — 아래), 비목표를 침범하지 않았다. `astream`은 `_record_call`이 sync + `asyncio.create_task` fire-and-forget이라 shield가 불필요하다는 계획의 판단이 코드로 확인됐다. 완주 경로 이중 차감 방어를 3곳 모두 테스트로 고정했다(계획이 "가장 그럴듯한 사고"로 지목한 것).
- **발산**:
  1. `chat_router`는 이미 `finally:` 블록이라 새 `except`가 아니라 **기존 `finally` 본문을 shield로 감싸는 것**이 맞았다. `finally`는 취소 시에도 실행되지만 첫 `await`(`add_message`)이 즉시 재취소돼 뒤의 차감에 도달하지 못하는 것이 실제 문제였다.
  2. 그 결과 **취소 시 부분 어시스턴트 메시지가 저장되게 됐다** — 그릴링을 거치지 않은 제품 동작 변화다. 저장과 차감을 분리하면 "돈은 받고 메시지는 버린다"가 되어 더 나쁘다고 판단했지만, 이 판단은 계획에 없었다.
  3. `_charge_sent` 사설 헬퍼를 라우터마다 하나씩 만들었다. 계획의 "래퍼로 추상화하지 않는다"는 사이트 간 공용 래퍼를 금지한 것이고, 이건 같은 함수의 완주·취소 두 경로가 동일 조건을 쓰게 하는 모듈 내부 헬퍼다.
  4. **계획의 S2 완성기준이 읽히는 것보다 약했다**(아래 학습 1).
  5. `_stream_work_chat_response`의 취소 단위 테스트는 구현 전에 이미 통과했다(기존 `finally` 때문). TDD의 red를 못 본 유일한 케이스.
  6. 테스트 파일 3개를 새로 만들었다(계획이 개수·위치를 정하지 않음). 3경로를 한 파일에 나란히 둔 이유는 "한 곳만 고치고 나머지를 잊는 것"이 이 작업의 가장 그럴듯한 사고이기 때문이다.
  7. `manuscript_router:126-127`의 stale 주석 2구절 정정(#63·#64 잔재), `ruff SIM117` 1건.

## Learnings

**1. 취소 관련 코드는 단위 테스트로 검증할 수 없다 — 거짓 green이 난다.**
shield를 임시 제거하고 실측한 결과: 실스택 통합 테스트는 red가 되는데 **단위 테스트 6건은 전부 green**이었다. 평범한 `task.cancel()`은 취소를 한 번만 전달하므로 핸들러 안의 후속 `await`이 그냥 성공하지만, 운영 경로는 anyio 태스크그룹 스코프 취소라 스코프가 취소 상태를 유지해 즉시 재취소한다. 즉 계획의 완성기준("취소하면 `record_usage`가 한 번 호출된다")만으로 봉인했다면 **조용히 한 토큰도 안 걷히는 코드**를 "검증됐다"고 기록했을 것이다.
→ **다음에**: 취소·타임아웃·연결 끊김이 걸린 변경은 **실서버 + 실클라이언트 끊김** 테스트를 완성기준에 넣는다. 그리고 방어 장치가 있으면 **그것을 제거했을 때 red가 되는지 직접 확인**한다(안 하면 방어하는 척하는 테스트가 남는다).

**2. "검증하지 않은 주장을 계획·보고에 넣는" 패턴이 네 사이클 연속 나왔다.**
#61 grep 범위를 확인했다고 거짓 기술(세 번째 소비자 놓침) → #62 표본 1개로 "이 모델은 그 증상이 없다" 단정(DB 로그로 40% 반박됨) → #64 식별자만 grep해 테스트 범위 절반 과소추정(4개 예상, 8개 필요) → #65 "shield 없이도 될 것"이라는 뻔한 구현. 이번엔 착수 전 실측이 잡아서 살았고, 그 실측을 한 이유는 #62의 교훈을 계획의 설계 원칙으로 적어뒀기 때문이다.
→ **다음에**: 계획·보고에 사실 주장을 쓸 때 **그 주장을 어떻게 확인했는지 한 줄을 같이 쓴다**. 확인 수단이 없으면 주장하지 않고 "확인 필요"로 남긴다. 이번 회고에서 `/hookify`로 훅 자동화를 시도했다.

**3. 그릴링을 거치지 않은 제품 동작 변화가 실행 중에 생길 수 있다.**
`chat_router` shield의 부수효과로 부분 어시스턴트 메시지 저장이 생겼다. 구조를 고치다 보니 딸려온 것이고, 기술적으로는 옳은 선택이지만 **제품 판단은 사용자 것**이다.
→ **다음에**: 실행 중 "계획에 없던 동작 변화"를 발견하면 run.md에 divergence로만 적지 말고 **회고에서 명시적 확인 과제로 올린다**. 이번엔 그렇게 했다(아래 후속).

**4. `Makefile` 참조 실패 12건을 두 사이클 연속 넘겼다.**
`Taskfile.yml`로 이전됐는데 테스트가 `Makefile`을 읽어 매 실행마다 12건이 실패한다. 그래서 "신규 실패 0"을 사람이 손으로 눈대중해야 한다 — 실제 회귀를 가릴 자리다.
→ **다음에**: 상시 실패하는 테스트는 발견 즉시 별도 과제로 올린다. 두 번 넘겼으면 세 번째도 넘긴다.

**5. 테스트에서 `asyncio.create_task`를 패치하면 테스트 자신의 태스크 생성까지 가로챈다.**
`asyncio.get_running_loop().create_task(...)`로 우회한다. (구현 세부 — 글로서리 대상 아님.)
