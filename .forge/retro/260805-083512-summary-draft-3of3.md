# 2026-08-05 — 늘려쓰기 (3/3): 요약으로 본문을 쓰고 화에 반영

## 계획 vs 실제

**계획대로 간 것**
- S1~S3의 골격 전부. `draft` 태스크 프론트 배선, 요약 선저장, 대체 확인, 완료 후 **일괄** 반영, `escapeHtml`, 전용 전이 ref(`prevDraftStreamingRef`).
- 계획의 "가장 그럴듯한 사고 셋"(ref 공유·취소인데 생성·escape 누락)은 모두 완성기준으로 못박혀 실제로 막혔다. 방어를 각각 깨뜨려 red를 확인하는 절차가 이번에도 유효했다.
- 계획 단계에서 실측해 둔 두 사실이 그대로 값을 했다 — `setContent`가 `onUpdate`를 쏘므로 늘려쓴 본문이 화 이탈 시 자동 저장된다, `restoreVersion`이 쓰는 문단 HTML 패턴을 그대로 재사용한다.
- DoD 6항목 충족. 최종 게이트: web typecheck·lint clean(224 files) · **342 passed (50 files)**.

**발산** (전체 9건은 `run.md`. 학습이 있는 것만)
1. **거짓 초록 두 번.** ① 계획의 완성기준 S3-②("생성 중 닫기 → 원고 무변경")가 통과했지만 이유가 틀렸다 — 테스트의 `stop` 목이 `vi.fn()`이라 `isStreaming`을 내리지 않는데, 실제 `stop()`(`assist.api.ts:202`)은 abort → `finally { setIsStreaming(false) }`로 **완료 전이를 만든다**. 운영에서는 닫기 직후 쓰다 만 생성물이 본문을 덮어썼다. ② z-index 건은 아래 3번.
2. **UI 형태가 UAT에서 네 번 바뀌었다.** 즉시 닫힘 → 진행 토스트 → 진행 다이얼로그 → 모달 시스템 통일. 레이블 4개 개칭과 편집란 높이도 같은 라운드에서 나왔다. 계획 그릴링으로는 여기까지 좁혀지지 않았다.
3. **`zIndex: 60` 진단이 틀렸고, 그걸 뒷받침한 테스트가 목표와 다른 명제를 봤다.** 1차 진단은 "양쪽 z-index가 50, Base UI가 DOM 순서로 이긴다"였고, 그 과정에서 `ModalDefault`가 `zIndex`를 선언만 하고 `Modal.Container`에 넘기지 않는 죽은 prop을 발견해 고치고 **렌더된 style을 단정하는 테스트로 red까지 확인했다.** 그래도 화면은 그대로였다. 실제 원인은 `Modal.Ground`의 `fixed inset-0 z-50`이 만드는 stacking context로, 자식의 z-index는 그 안에서만 경쟁한다.
4. **일괄 치환 사고.** `저장` → `요약 저장`을 파일 전체에 치환해 칩 줄의 **화 저장** 버튼을 가리키던 테스트 6곳을 깨뜨렸고 5건이 red로 떨어졌다. 각 위치의 `describe`를 확인해 모달 저장 2곳만 남겼다. 프로덕션 영향 없음.
5. **도달 불가능한 방어를 넣었다가 되물렸다.** 요약 완료 효과의 `|| draftingBody` 게이트는 제거해도 초록이었다 — 늘려쓰기 중 `summaryPhase`는 항상 `'idle'`이라 앞 조건이 이미 막는다. 지웠다.

## 학습

**다음에 다르게 할 것**

- **"red가 된다"를 "옳은 것을 검증한다"로 착각하지 말 것.** 방어를 깨서 red를 확인하는 절차는 유효하지만, 그 위에 질문이 하나 더 필요하다 — *이 테스트가 보는 명제가 목표와 같은가?* #71의 z-index 테스트는 "style에 값이 붙는다"를 정확히 증명했고 red도 났지만, 목표는 "위에 그려진다"였다. → 훅 6번 항목으로 자동화했다.
- **jsdom이 관측할 수 없는 것을 테스트로 증명했다고 적지 말 것** — 페인팅·레이아웃·쌓임 순서·실제 크기. 테스트로는 *메커니즘*만 고정하고(같은 시스템·같은 층·나중 오픈), 결과는 브라우저 확인에 맡긴다. 이번에 CSS 값(`min-h`)과 `twMerge` 병합 결과는 테스트·빌드로 확정했지만 "270px로 보인다"는 사람이 봐야 했다.
- **목이 부작용을 재현하지 않으면 테스트는 실제 경로를 가린다.** `vi.fn()` 목은 "불렸다"만 알려주고, 실제 함수가 일으키는 상태 변화(`stop()` → `isStreaming: false`)는 재현하지 않는다. 취소·중단·abort 계열을 테스트할 때는 **그 부작용까지 목에 넣어야** 한다(`act(() => setMockAssistState({ isStreaming: false }))`). 이 저장소에서 "테스트 초록 + 실제 경로 깨짐"의 **네 번째** 유형이다(앞선 셋: anyio 취소 스코프, 타입 유니온 목 우회, 손조립 응답의 기본값 `None`).
- **UI 작업은 UAT 라운드를 형태 결정 단계로 계획할 것.** 계획의 UAT 항목을 "동작하는가"로만 잡으면 모달 흐름·문구·크기 같은 결정이 전부 UAT 이후로 밀려 라운드가 늘어난다. 다음 UI 작업의 계획에는 "UAT에서 형태가 바뀔 수 있는 지점"을 미리 적고(닫는 시점, 진행 표시 위치, 중단 수단), 가능하면 fg-visual로 그릴링 때 보여 준다.
- **레이블 개칭은 파일 전체 치환하지 말 것.** 같은 낱말이 다른 버튼을 가리킨다. 치환 전에 각 출현 위치가 어느 컴포넌트·`describe`인지 확인한다.
- **모달 시스템이 둘 공존한다는 사실을 먼저 확인할 것.** 새 확인창을 붙일 때 "겹칠 상대가 어느 시스템인지"를 보고 고른다 — 규칙은 ADR `260805-082723`.

**확인된 것 (유지)**
- 방어를 하나씩 제거해 red를 확인하는 절차. 이번 사이클에 7개를 검증했고 1개(`|| draftingBody`)를 도달 불가로 걸러냈다.
- 계획 단계의 선실측(`setContent` → `onUpdate`). 이걸 안 했다면 "화면엔 보이는데 화를 옮기면 사라진다"는 조용한 유실을 만들 수 있었다.
- `openModal` 목을 없애고 실제 확인창을 렌더해 조작하는 테스트 방식 — 부수적으로 얻었지만 목이 실제 경로를 가리던 문제가 함께 사라졌다.

## 문서 갱신
- CONTEXT.md 승급: **늘려쓰기 (Draft from Summary)** 항목에 "UI 레이블은 `요약으로 본문 작성`" 명기(용어 자체는 유지 — [[메모리]]가 내부 개념이고 화면 문구는 따로인 것과 같은 분리).

- 훅 갱신: `.claude/hooks/forge-claim-check.py`에 6번 항목 추가("red ≠ 목표 검증" + jsdom 관측 불가 목록). 기존 동적 항목은 7번으로 밀었고, 6·7번이 각각 1회만 나오는 것을 실행으로 확인.

## 후속 작업 후보
- **앱 전반의 `useModal` → Base UI `Dialog` 통일** — `work-tree.tsx`의 확인창 4곳 등. 지금은 Base UI 모달과 겹치지 않아 정상 동작하므로 급하지 않다.
