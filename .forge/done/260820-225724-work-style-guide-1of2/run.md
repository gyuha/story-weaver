## 발산

1. **S3가 저장 경로를 범용 `PATCH /api/v1/works/{work_id}`로 정했다**(계획이 S3에 맡긴 판단). 근거: `style_note`는 `art_style_note`처럼 별도 하위 리소스(화풍 카탈로그 검증)에 얽히지 않은 평범한 Work 컬럼이고, `WorksService.update_work`가 이미 `model_dump(exclude_unset=True)` + `setattr`인 범용 로직이라 스키마에 필드만 더하면 서비스 코드 변경이 0이다. 화풍이 전용 엔드포인트를 가진 것은 카탈로그 검증이라는 별개 책임 때문이지 "새 필드마다 전용 엔드포인트"라는 패턴이 아니다. **타당한 판단이라고 본다.**
2. **삽입 위치를 문맥별로 다르게 했다** — `chat_context_service`·`prompt_assembler`는 별도 문단으로, `manuscript_router`·`works_router`는 프롬프트 **맨 끝에 별도 문장**으로 붙였다. 후자는 원본이 접속 어구로 이어지는 단일 문장이라 중간 삽입 시 문법이 깨지기 때문이다. task 81의 마침표 겹침을 의식한 선택이다.
3. **`assemble_prompt`에 기본값 `None`을 둬 하위 호환을 유지했다** — 계획은 "인자 추가로 깨지는 기존 테스트를 함께 고쳐라"고 했으나 키워드 전용 기본값으로 아예 깨지지 않게 했다. 계획의 지시보다 나은 처리다.
4. **S4가 완료 기준 하나를 잘못 판정했다 — 이 실행에서 가장 중요한 사건.** 계획의 S3 완료 기준은 *"브라우저에서 입력란이 보이고 저장 후 새로고침해도 값이 남는 것을 **눈으로** 확인"*인데, S4는 **RTL 테스트를 근거로 "충족"이라 판정**했다. jsdom은 렌더 여부를 알려주지만 계획이 요구한 것은 브라우저 확인이었다. 계획의 검증 노트 3번이 정확히 이 함정을 경고했는데도 검증 담당이 그것을 넘어갔다.
   - **그래서 메인 세션이 UAT로 보완했다**(아래 UAT 절). 결과적으로 미충족은 없었지만, **검증 담당이 "무엇으로 확인했는지"를 완료 기준과 대조하지 않으면 통과 판정이 신뢰를 잃는다**는 것이 이번의 교훈이다.
5. **`Work` 타입에 필드가 늘며 기존 프론트 픽스처 15개 파일에 `styleNote: null`을 한 줄씩 넣었다** — 타입 정합성 유지 목적이고 로직 변경은 없다. 변경 파일 43개 중 상당수가 이것이라 diff가 실제 작업량보다 커 보인다.
6. **서버 `--reload`가 이번에는 걸렸다** — 지난 세션에서는 코드를 고쳐도 워커가 재시작되지 않아 구코드로 돌았는데(그래서 수동 재시작이 필요했다), 이번에는 `/openapi.json`에 `styleNote`가 즉시 나타났다. 즉 그 현상은 항상 재현되는 것이 아니다.

## 방어를 깨뜨려 red를 확인한 것

- **S4가 "지침 없으면 미주입" 방어를 직접 깨서 확인했다.** `prompt_assembler`의 `if work_style_note:` 분기를 제거해 항상 주입하게 바꾸니 **17 failed**, 실패 메시지가 `assert '작가가 지정한 문체 지침' not in ... / '작가가 지정한 문체 지침: None'`이었다. 즉 이 테스트는 **빈 값이 `문체 지침: None` 껍데기로 새는 것**을 정확히 잡는다. 원복 후 42 passed로 복귀하고 `git diff`로 잔여물이 없음을 확인했다.
- 계획이 요구한 "양방향(포함/미포함)" 중 **미포함 쪽이 실제로 방어하는지**가 이것으로 증명됐다 — 포함만 테스트했다면 껍데기 주입을 놓쳤을 것이다.

## UAT — 실 스택에서 확인 (메인 세션이 수행)

발산 4 때문에 메인 세션이 직접 했다. 사용자 작품 데이터를 바꾸지 않으려고 **저장 왕복은 QA 작품의 실 API로, 화면 렌더는 브라우저로** 나눴다.

1. **실 API 왕복** — QA 작품에 `PATCH {"styleNote":"건조한 하드보일드. 3인칭 제한 시점. …"}` → 응답과 `GET` 재조회가 값을 그대로 돌려줬다.
2. **브라우저 렌더**(`aside-browser`, `/works/{workId}/synopsis`) — 라벨 `문체 지침`, `textarea#synopsis-style-note`(4행), placeholder `예: 건조한 하드보일드, 3인칭 제한 시점, 감정 설명 금지 (비워도 됩니다)`, 버튼 `문체 지침 저장`/`문체 지침 취소`가 **기획의도 아래에 같은 확정 방식으로** 렌더되는 것을 스크린샷으로 확인했다. 버튼 접근성 이름을 분리해 기존 `저장`/`취소` 테스트와 충돌하지 않게 한 것도 확인됐다.
3. **실 프롬프트 주입 — 대조군까지 얻었다.** QA 작품으로 비트 시트 생성(`POST /works/{id}/beat-sheet`)을 호출하고 `llm_call_logs`의 `messages`를 직접 조회했다:
   - `12:51:19` (지침 설정 **전**) → 문체 지침 **미포함**
   - `12:55:35` (지침 설정 **후**) → **포함**: `…줄 목록만 출력하세요. 작가가 지정한 문체 지침: 건조한 하드보일드. 3인칭 제한 시점. 감정을 설명하지 말고 행동으로 보여라.`
   같은 작품·같은 엔드포인트에서 **설정 전후가 갈린다** — 목이 아니라 실 DB·실 프롬프트에서 조건부 주입이 동작한다는 증거다.
4. `alembic current` → `0007_work_style_note (head)`, `/openapi.json`의 `WorkResponse`·`WorkUpdate`에 `styleNote` 존재.
