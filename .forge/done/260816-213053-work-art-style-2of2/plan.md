# 작품 화풍 (2/2): `이미지 스타일` 메뉴·화면과 카드 생성 영역 정리

## 목표 / 비목표

- 목표: 작가가 [[작품 화풍]]을 실제로 정할 수 있게 한다 — 좌측 작품 내비에 `이미지 스타일` 항목과 전용 화면(화풍마다 유형 견본 3장 · 작품 톤 한 줄 · 저장 · 변경 시 확인창)을 만들고, 카드 상세의 **템플릿 썸네일 그리드를 걷어내고** 적용될 화풍을 한 줄로 알리며, 화풍이 없으면 생성을 막고 스타일 화면으로 유도한다.
- 비목표: 백엔드 변경 일체(1/2에서 끝났다) — **스펙이 부족하면 여기서 고치지 말고 기록하고 멈춘다**(task 78이 이 문장 덕에 계약 공백을 제때 잡아 task 79를 낳았다). 새 작품 위저드에 화풍 단계 추가. 구도 선택 UI 부활. 좌측 목록(18×18)·관계도의 대표 이미지 썸네일(카드별 대표를 한 번에 주는 벌크 엔드포인트가 없어 task 78이 이모지로 고정했다 — 그 상태를 유지한다).

## 진실의 출처

- 글로서리 용어: **작품 화풍**(코드·문서 용어) — **화면 레이블은 `이미지 스타일`**이다. 메뉴 이름·화면 제목·본문 문구에는 `이미지 스타일`을 쓰고, 변수·파일명·주석에는 `art style`/작품 화풍을 쓴다([[늘려쓰기]]가 같은 분리를 갖는다). 함께: **이미지 템플릿**(정의가 바뀌어 화풍이 빠졌다) · **설정 이미지** · **대표 이미지** · **시각 묘사**.
- 관련 ADR: `.forge/adr/260813-110724-work-owns-art-style-templates-own-composition.md` — **먼저 읽을 것.** 특히 Consequences의 두 줄이 이 작업의 근거다: "카드 상세의 템플릿 썸네일 그리드가 사라진다(선택지 하나짜리 그리드는 사용자를 속이는 UI다)"와 "화풍이 정해지지 않은 작품에서는 이미지를 생성할 수 없다". 함께: `260805-082723`(Base UI 모달 위에 겹치는 모달은 Base UI `Dialog`로만 — 확인창을 띄우므로 적용).
- 기존 코드(전부 읽어 확인): `web/src/components/layout/work-shell.tsx` — `WorkSection = 'write' | 'bible' | 'synopsis' | 'timeline'`(9행)과 기능 메뉴 블록의 `NavItem` 3개(30-51행: 시놉시스 `FileText` · World Bible `Sparkles` · 검토 · 타임라인 `Clock`). `web/src/features/world-bible/components/entity-image-section.tsx`(task 78이 만든 단일 파일 — 템플릿 그리드·생성·스트립·묘사가 여기 다 있다) · `lib/use-entity-images.ts` · `lib/use-generate-entity-image.ts` · `api/entity-images.api.ts`(`apiImageSrc()`로 `VITE_API_BASE_URL`을 붙인다 — 견본 URL에도 필요하다). 라우트는 `web/src/routes/works/$workId/`에 파일을 만들면 생성된다(`routeTree.gen.ts`는 손대지 않는다).
- Definition of Done: 좌측 내비의 `이미지 스타일`을 누르면 화풍 4개가 **각각 유형 견본 3장과 함께** 뜨고, 하나를 골라 톤을 적고 저장하면 다시 들어와도 그대로다. 이미 이미지가 있는 작품에서 화풍을 바꾸면 **확인창이 "이미 만든 N장은 그대로 남고 앞으로 생성하는 이미지만 새 화풍을 따릅니다"를 고지**한다. 카드 상세에 **썸네일 그리드가 없고** 적용될 화풍이 한 줄로 보이며 그 링크가 스타일 화면으로 간다. 화풍이 없는 작품의 카드에서는 `생성` 대신 유도 문구가 보인다. `pnpm typecheck`·`pnpm lint`·`pnpm test` 통과.

## 작업 조각

- [ ] S1. `pnpm generate` + 계약 확인 — completion criterion: 1/2이 갱신한 `docs/openapi.json`에서 `src/api`를 재생성해 화풍 카탈로그·작품 화풍 GET/PUT SDK 함수가 생기고, SSE 생성 요청 바디에 `templateId`가 **없다**. `pnpm typecheck` 통과. **1/2이 `/image-templates`를 지웠는지 남겼는지 여기서 확인**하고(그 결정은 1/2의 `run.md`에 있다) 이후 슬라이스가 무엇을 부를지 정한다.

- [ ] S2. 내비 항목 + 라우트 (TDD) — completion criterion: `WorkSection`에 `'artStyle'`(또는 동등한 값)을 추가하고 `work-shell.tsx`의 기능 메뉴 블록에 **네 번째 `NavItem`** `이미지 스타일`을 넣는다(아이콘은 `lucide-react`에서 이미 쓰는 것 중 고르되 `Sparkles`는 World Bible이 쓰고 있으니 피한다 — 예 `Palette`). 라우트 파일을 `src/routes/works/$workId/`에 만든다. 완성기준: 내비에서 누르면 그 라우트로 가고 활성 표시가 그 항목에 붙는다(vitest — 기존 세 항목의 활성 전이가 깨지지 않는 것까지 단정).

- [ ] S3. `이미지 스타일` 화면 — 화풍 선택 (TDD) — completion criterion: 화풍 4개를 **한 줄에 유형 견본 3장씩**(인물·장소·아이템) 보여준다(그릴링에서 fg-visual로 확정한 C안 — 결정의 본질이 "내 작품 전체가 이 화풍으로 보인다"를 판단하는 것이므로 인물 견본만으로는 부족하다). 선택 상태가 시각적으로 구분되고, 현재 작품의 화풍이 선택된 상태로 뜬다. 견본 URL은 `apiImageSrc()`를 거친다. 견본이 404인 경우 깨진 이미지가 노출되지 않게 처리한다(task 78이 `onError`로 한 것과 같은 방식 — 지금 16장 전부 있지만 방어는 남긴다). vitest — 화풍 4개 렌더 · 각 줄에 견본 3장 · 현재 화풍이 선택 상태 · 견본 404가 깨진 이미지로 노출되지 않음. (depends: S1)

- [ ] S4. 작품 톤 입력 + 저장 + 변경 확인창 (TDD) — completion criterion: 화풍 아래 **한 줄 입력**(작품 고유의 톤, 비워도 됨)과 `저장`. 저장은 `PUT .../art-style`. **이미 [[설정 이미지]]가 1장 이상 있는 작품에서 화풍을 바꿀 때만** 확인창을 띄우고 "이미 만든 N장은 그대로 남고, 앞으로 생성하는 이미지만 새 화풍을 따릅니다"를 고지한다(ADR — 잠금 대신 고지를 택한 이유가 여기다). 확인창은 Base UI `Dialog`로 띄운다(ADR `260805-082723`). **Enter/Backspace로 커밋하는 입력을 만들지 않는다** — 별도 `저장` 버튼이므로 한글 IME 함정을 구조적으로 회피한다(`new-work-creation-wizard` 회고). vitest — 저장이 PUT을 1회 보냄 · 이미지 0장이면 확인창 없이 저장 · 이미지 1장 이상 + 화풍 변경이면 확인창이 뜨고 취소하면 PUT이 안 나감 · 톤만 바꾸면 확인창 없음(화풍이 그대로이므로) · 실패 시 이동·초기화 없이 에러 토스트. (depends: S1, S3)

- [ ] S5. 카드 상세 정리 — 그리드 철거 + 화풍 한 줄 + 미지정 유도 (TDD) — completion criterion: `entity-image-section.tsx`에서 **템플릿 썸네일 그리드와 그 조회 훅을 제거**하고, 대신 적용될 화풍을 한 줄로 보여준다(예: `이 작품의 화풍: 수묵화 · 바꾸기` — `바꾸기`가 스타일 화면 링크). `추가 지시` 입력과 `생성` 버튼은 남는다. **화풍이 없으면 `생성` 대신 유도**(`먼저 이 작품의 화풍을 정해 주세요 → 이미지 스타일`)를 보여준다. 생성 요청에서 `templateId`를 보내지 않는다. **철거로 고아가 된 것만 정리**하고 무관한 코드는 건드리지 않는다. vitest — 그리드가 렌더되지 않음 · 화풍 한 줄이 보이고 링크가 맞음 · 화풍 없으면 `생성` 버튼이 없고 유도가 보임(그 분기를 제거해 red 확인) · 생성 요청 바디에 `templateId`가 없음 · 기존 스트립·대표 지정·묘사 편집 테스트가 그대로 초록. (depends: S1)

- [ ] S6. 검증 — completion criterion: `cd web && pnpm typecheck` · `pnpm lint` · `pnpm test` 전부 통과. **테스트 순감이 있으면 `git stash`로 기준선을 재현해 파일별로 대조하고 의도한 만큼만 줄었는지 기록한다**(task 75·78에서 이 절차가 값을 했다 — 그리드 테스트가 사라지므로 반드시 줄어든다). `grep -rn "template" src/features/world-bible/`로 템플릿 잔존 참조를 확인하고 남은 것이 있으면 그 이유를 적는다. 그리고 아래 "UAT 지시"를 사람이 수행한다. (depends: S1–S5)

## UAT 지시 (사람이 확인할 것 — 화면 경로와 레이블은 코드에서 인용)

`cd api && task dev`(:8000) + `cd web && pnpm dev`(:3000), 자기 계정으로 로그인한 뒤:

1. 작품을 열고 좌측 내비의 **`이미지 스타일`**을 누른다 → 화풍 4개가 **각각 견본 3장과 함께** 뜨는지, 견본이 실제 그림으로 렌더되는지(깨진 아이콘이면 견본 URL 문제).
2. 화풍 하나를 고르고 톤에 한 줄 적고 `저장` → 다른 화면에 갔다 돌아와도 그대로인지.
3. World Bible의 인물 카드로 간다 → **썸네일 그리드가 없고** `이 작품의 화풍: …` 한 줄이 보이는지, 그 링크가 스타일 화면으로 가는지.
4. `생성`을 눌러 이미지를 만든다 → 방금 정한 화풍으로 그려지는지(**이것이 이 작업의 핵심 확인**이다 — 톤까지 반영되면 더 좋다).
5. `이미지 스타일`로 돌아가 **화풍을 다른 것으로 바꾼다** → 확인창이 "이미 만든 1장은 그대로 남고…"를 고지하는지. 확인하고 카드로 돌아가 다시 `생성` → 새 화풍으로 나오고 **이전 장이 스트립에 그대로 있는지**.
6. 화풍이 없는 작품(기존 작품 4건 중 하나)의 카드로 간다 → `생성` 대신 유도 문구가 보이는지.

**브라우저로 관측하려 하지 말 것**: 생성 중 취소·낙관적 갱신 순서 — 타이밍 의존이라 테스트로 고정한다.

## 검증 노트

**그릴링 중 확인한 것**

- 내비 구조: `work-shell.tsx:9`의 `WorkSection` 유니온과 30-51행의 `NavItem` 3개를 읽어 확인. **네 번째 항목 추가는 새 섹션 값 하나·NavItem 하나·라우트 하나**로 끝난다.
- `Sparkles` 아이콘은 World Bible이 쓰고 있다(40행 `iconClassName="text-ai"`) — 화풍에 같은 아이콘을 쓰면 헷갈린다.
- task 78이 만든 구조: `entity-image-section.tsx` 단일 파일 + 훅 2개 + API facade. **그리드가 그 파일 안에 있으므로 철거 지점이 한 곳이다.**
- `apiImageSrc()`가 host 없는 절대경로에 `VITE_API_BASE_URL`을 붙인다(task 78의 발산 3) — **견본 URL도 이걸 거쳐야 prod에서 깨지지 않는다.**
- 좌측 목록(18×18)은 task 78이 이모지로 고정했고 그 이유(행마다 요청·벌크 엔드포인트 부재)는 그 `run.md`에 있다. **이 작업에서 되살리려 하지 말 것** — 비목표다.

**확인 필요** (실행 중 실측할 것)

- **1/2이 `/image-templates`를 지웠는지 남겼는지**(S1). 남겼다면 S5에서 그 훅을 지울 때 백엔드가 여전히 그것을 서빙하는 상태가 된다 — 그 자체는 문제가 아니지만 `run.md`에 적어 다음 사람이 놀라지 않게 하라.
- **화풍 견본 3장을 한 줄에 넣었을 때 실제 폭에서 어떻게 보이는지.** 그릴링 목업에서 52px로 잡았으나 실제 화면 폭·사이드바 폭에 따라 달라진다 — **jsdom은 이걸 관측할 수 없다**(페인팅·실제 크기). UAT 1번의 몫이다.
- **화풍을 바꾼 뒤 카드 화면의 "이 작품의 화풍" 한 줄이 즉시 갱신되는가.** 쿼리 캐시 무효화가 필요하다 — 낡은 값이 보이면 스타일 저장 후 관련 쿼리를 invalidate하라. 테스트로 고정하고 UAT 5번에서도 본다.

**이 저장소가 반복한 함정**

- **철거는 조용히 과하게 지우기 쉽다.** S5·S6이 그 위험을 진다 — 일괄 치환·일괄 삭제 금지, 지운 뒤 테스트 수를 세어 의도한 만큼만 줄었는지 확인(task 75가 `git stash` 기준선 대조로 -9건을 전부 설명했다).
- **목이 부작용을 재현하지 않으면 테스트가 실제 경로를 가린다**(이 저장소의 네 번째 사고 유형). S4의 확인창 테스트는 "확인창이 떴다"가 아니라 **취소했을 때 PUT이 나가지 않는 것**까지 단정해야 한다.
- **red가 된다 ≠ 목표 검증.** S5의 미지정 유도 테스트는 "문구가 있다"가 아니라 **`생성` 버튼이 없다**를 함께 봐야 한다(문구만 추가하고 버튼을 남기면 통과해 버린다).
- **jsdom이 관측할 수 없는 것을 테스트로 증명했다고 적지 말 것** — 견본 3장의 실제 크기·줄바꿈은 브라우저에서만 확인된다.
