# 집필 보조 태스크별 온도 테이블을 둔다

## 목표 / 하지 않을 것

- **목표**: 지금 전역 `1.0`인 샘플링 온도를 태스크 성격에 맞게 가른다 — 창작 계열은 0.7, 결정적 작업은 0.2. `TASK_TIER` 옆에 `TASK_TEMPERATURE`를 두고 요청별로 전달한다.
- **하지 않을 것**:
  - **작가에게 온도를 노출하기** — `ADR-0004`가 "사용자는 모델명·저수준을 직접 다루지 않는다"고 정했고 [[품질 티어]]가 그 추상이다. 온도는 앱이 정한다.
  - **`.env`의 전역 기본값(`LLM_TEMPERATURE=1.0`) 변경** — 그릴링에서 테이블 방식을 골랐다. 테이블이 닿지 않는 경로(채팅·비트 시트·기획의도 이어쓰기)는 이번에 손대지 않는다(아래 미해결 항목).
  - 문체 지침 관련 작업 — part 1/2.

## 참조 근거

- **글로서리**: [[품질 티어]] · [[문체]] · [[문체 지침]] (`.forge/CONTEXT.md`)
- **관련 ADR**: `ADR-0004`(사용자는 저수준을 직접 다루지 않는다 — 온도를 노출하지 않는 근거)
- **새 ADR 없음** — 상수 테이블이라 되돌리기 쉽다. 다만 아래 "근거의 한계"를 계획에 남겨 나중에 값을 재검토할 수 있게 한다.
- **완료 정의**: 집필 보조 8종이 각자의 온도로 호출되고, 그 값이 테스트로 고정된다. `task test`·`task lint` 통과.

## 이 계획이 딛고 있는, 그릴링에서 확인한 사실

1. **현재 온도는 전역 `1.0`** — `api/.env`의 `LLM_TEMPERATURE=1.0`, 정의는 `core/config.py:109-113`("0.0 is deterministic; 2.0 is highly creative"). 받은 조언의 권고(0.6~0.7)보다 높다.
2. **태스크별로 가를 자리가 이미 있다** — `assist/tier_routing.py:60-71`의 `TASK_TIER`가 태스크→티어를 매핑한다(8종 전부 등재). 온도도 같은 형태의 테이블로 둘 수 있다.
3. **요청별 온도 전달 경로가 있다** — `chat/llm_client.py:108,119`가 `override_kwargs`로 per-request `temperature`를 받는다고 명시한다. `ports.py:329,378`도 `temperature`를 공통 키로 문서화한다.
4. **태스크별 온도의 선례는 없다** — `grep -rn temperature api/src`의 결과 중 `provider_factory.py:60`은 **docstring 예시**이고 실제 호출이 아니다. 즉 이번이 첫 도입이다.
5. **두 티어가 지금 같은 클라이언트로 해석된다** — `tier_routing.py:72-74` 주석이 밝힌다(모델이 하나뿐). 온도는 티어와 **다른 축**이므로 티어에 얹지 않는다: `correct`와 `continue_`가 둘 다 `low_cost`인데 필요한 온도는 반대다.

## 작업 조각

- [ ] **S1. `TASK_TEMPERATURE` 테이블과 전달 배선** — `tier_routing.py`에 태스크→온도 매핑을 두고 assist 호출 경로가 그 값을 요청별로 넘기게 한다. 값의 초안: `continue_`·`infill`·`dialogue`·`style`·`draft` = **0.7**(창작), `correct`·`title_`·`summary` = **0.2**(결정적). 완료 기준: 8종 전부가 테이블에 등재되어 있고(`TASK_TIER`와 키 집합이 같은지 단언 — 태스크가 늘 때 누락되면 red), 각 태스크 호출이 **자기 온도를 실제로 전달하는 것**을 테스트로 고정한다. "테이블에 값이 있다"가 아니라 "그 값이 클라이언트까지 간다"를 봐야 한다.
- [ ] **S2. 검증** — 완료 기준: `task test` 통과(errors 0) · `task lint`(ruff + mypy) 클린. 온도가 실제 생성 결과를 어떻게 바꾸는지는 **측정하지 않는다**(아래 근거의 한계).

## 검증 노트

1. **근거의 한계를 정직하게 남긴다.** 0.7/0.2는 **받은 조언과 일반 통념에 기댄 값이고 이 저장소에서 측정한 값이 아니다.** 문체가 실제로 덜 흔들리는지는 같은 프롬프트를 여러 온도로 여러 번 돌려 비교해야 알 수 있고, 그것은 이 계획의 범위가 아니다. 값을 바꿀 근거가 생기면 테이블 한 줄이므로 쉽게 조정된다 — 그래서 ADR로 굳히지 않았다.
2. **"테이블에 있다"와 "전달된다"는 다른 명제다.** 상수만 단언하는 테스트는 배선이 끊겨도 green이다 — task 82의 교훈(`zIndex` 값은 붙었지만 목표는 달성되지 않았던 #71 사례)과 같은 함정이다. S1의 완료 기준이 전달을 보는 이유다.
3. **테이블이 닿지 않는 경로가 남는다(의도된 미해결)** — 채팅(`chat_context_service`), 비트 시트(`works_router:161`), 기획의도 이어쓰기(`manuscript_router:177`)는 assist 경로가 아니라 전역 `1.0`을 그대로 쓴다. 이 셋을 어떻게 할지는 후속 판단 거리다.
4. **`task test`의 기존 무관 실패 12건**(`Makefile` 부재)과 `test_stream_cancel_shield`의 간헐 실패를 새 결함으로 오인하지 말 것. **errors 0**이 판단 기준이다.
