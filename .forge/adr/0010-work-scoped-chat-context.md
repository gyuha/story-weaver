# 작품 단위 채팅 — 매 턴 프레시 컨텍스트 조립, 현재 화 범위로 제한

집필 화면의 "채팅" 탭을 mock에서 실제 LLM 연동으로 바꾸면서, 네 가지를 함께 결정했다.

1. **대화는 씬이 아니라 작품(Work) 단위로 유지된다.** 씬을 옮겨도 대화가 끊기지 않는다. `chat.conversations`에 `work_id`(nullable FK, `works.id`)를 추가하되 `(user_id, work_id)` 유니크 제약은 두지 않는다 — "새 대화 시작"이 같은 작품에 새 `Conversation` row를 하나 더 만들 수 있어야 하기 때문이다. "현재 대화"는 해당 `work_id`를 가진 대화 중 가장 최근 것으로 정의한다. 과거 대화를 다시 불러보는 UI는 이번 범위 밖(비목표) — 필요해지면 별도 과제.
2. **컨텍스트(원고·설정)는 매 메시지마다 새로 조립하고, DB에는 영속화하지 않는다.** `Conversation.system_prompt` 칼럼(대화 생성 시 고정)은 이 기능에는 쓰지 않는다 — 사용자가 채팅 중에도 원고를 계속 고쳐 쓰므로, 고정된 컨텍스트는 금방 낡는다. 매 호출 직전에 "현재 화 전문 + 메모리 검색 결과"로 임시 시스템 메시지를 만들어 DB에 쌓인 실제 user/assistant 턴 앞에 붙여서 보낸다. DB에는 순수 대화 이력만 남는다.
3. **원고 컨텍스트 범위는 "현재 화(챕터) 전체"로 제한한다. 작품 전체 원고를 통째로 넣지 않는다.** 연재형 웹소설은 화수가 쌓이면 컨텍스트 윈도우·비용이 반드시 깨진다. 화 단위로 잘라 안전한 상한을 두었다. "작품 전체를 알아야 답할 수 있는 질문"은 커버하지 못하지만, 이는 요약(summary) 기능이 먼저 필요한 별도 과제로 남긴다.
4. **다른 LLM 기능과 동일한 인프라를 재사용한다.** 티어는 `high_quality`(thinking 모드 켬 — 이어쓰기 등 5개 작업과 달리 채팅은 분석적 질의응답이라 속도보다 추론 품질이 맞다), 예산 게이트(`require_budget_available`/`record_usage`), rate limit, 수위 검열(`is_explicit_content` + `stream_with_retry`)까지 assist 도메인과 동일 정책.

## Considered Options

- 작품 전체 원고 전문을 항상 포함 — 거부. 화수가 쌓이면 반드시 깨지는 방식이고, 지금은 요약 기능이 없어 대안도 없다.
- 씬 단위 대화(씬을 옮기면 새 대화) — 거부. 사용자가 "전체 글" 기준 질의를 기대했고, 씬마다 대화가 끊기면 그 기대에 어긋난다.
- 대화 생성 시 컨텍스트를 한 번만 고정(`system_prompt` 사용) — 거부. 구현은 간단하지만 집필이 진행될수록 챗봇이 옛 내용으로 답하는 문제가 즉시 발생한다.
- `(user_id, work_id)` 유니크 제약으로 작품당 대화 1개 강제 — 처음 채택했다가, "새 대화 시작" 요구사항이 나오며 폐기(여러 대화 허용 + "최근 것 = 현재"로 대체).
